Define tools as regular `ai-tool` routes and give them tags:

[source,java]
----
from("ai-tool:query_db?tags=crm&description=Query customer database"
     + "&parameter.customerId=string&parameter.customerId.required=true")
    .to("jdbc:dataSource");
----

or in YAML DSL:

[source,yaml]
----
- route:
    from:
      uri: "ai-tool:send_email"
      parameters:
        description: "Send email notification"
        tags: "notify"
        parameter.to: string
        parameter.to.description: "Recipient address"
        parameter.to.required: "true"
        parameter.subject: string
        parameter.priority: string
        parameter.priority.enum: "low,normal,high"
      steps:
        - to: "smtp://mail.example.com"
----

Tool parameters are declared with the `parameter.NAME` options: the value is
the JSON type (`string`, `integer`, `number`, `boolean`), and the
`parameter.NAME.description`, `parameter.NAME.required` and
`parameter.NAME.enum` options refine the generated JSON Schema. Arguments
arrive as message headers in the route (`${header.customerId}`).

Select the tags to expose in `application.properties`:

[source,properties]
----
camel.mcp-server.tags = crm,notify

# per-call tool execution timeout (milliseconds, default 20000)
camel.mcp-server.tool-timeout = 10000
# per-read resource execution timeout (milliseconds, default 20000)
camel.mcp-server.resource-timeout = 10000
# per-request prompt execution timeout (milliseconds, default 20000)
camel.mcp-server.prompt-timeout = 10000
----

=== Resources and resource templates

Expose a fixed resource with an `ai-resource` route. The route body supplies
the resource content and the component metadata supplies its URI and MIME type:

[source,java]
----
from("ai-resource:app_config?resourceUri=camel:///config/app.json"
     + "&tags=crm&description=Application configuration&mimeType=application/json")
    .setBody(constant("{\"env\":\"production\"}"));
----

A resource template can expose resources selected by URI path variables:

[source,java]
----
from("ai-resource:customer_template?uriTemplate=camel:///customers/{customerId}"
     + "&tags=crm&description=Customer selected by id&mimeType=application/json")
    .process(exchange -> {
        String customerId = exchange.getMessage().getHeader(
                "CamelAiResourceTemplateVariable.customerId", String.class);

        // Validate the identifier against application policy before using it.
        if (customerId == null || !customerId.matches("[A-Za-z0-9-]{1,64}")) {
            throw new IllegalArgumentException("Invalid customer identifier");
        }

        exchange.getMessage().setBody("{\"customerId\":\"" + customerId + "\"}");
    });
----

A route declares either `resourceUri` for a fixed resource or `uriTemplate`
for a resource template. Template variables are client input: validate them
before using them in filesystem paths, database queries, authorization
decisions, or downstream requests. Do not treat a syntactically valid URI
variable as proof that the caller may access the referenced data.

Resources and resource templates are selected using the same
`camel.mcp-server.tags` setting as tools. Their registration follows the
Camel route lifecycle.

=== Prompts

Expose a prompt with an `ai-prompt` route. Prompt arguments are strings and
arrive as message headers:

[source,java]
----
from("ai-prompt:greeting?tags=crm&description=Say hello&title=Greeting"
     + "&argument.name.description=Who to greet&argument.name.required=true")
    .setBody(simple("Hello ${header.name}"));
----

A string route result becomes one user message. For a multi-message result,
return a list containing strings and/or maps with `role` and `content` fields.
The supported roles are `user` and `assistant`. Content may be plain text or
an MCP content block:

[source,java]
----
from("ai-prompt:multi_turn?tags=crm&description=Return a user and assistant message")
    .setBody(constant(List.of(
        "Plain user message",
        Map.of("role", "assistant", "content", "Assistant reply"))));
----

Prompt routes follow the same tag selection and route lifecycle rules.
Content assembled from external systems, including resource content and
prompt messages, must be treated as untrusted data. It may contain prompt
injection instructions; do not grant such content authority over system
instructions, tool permissions, or application security policy.

To advertise resource and prompt capabilities and their list-change
notifications, configure the corresponding Spring AI server properties:

[source,properties]
----
spring.ai.mcp.server.capabilities.resource = true
spring.ai.mcp.server.capabilities.prompt = true
spring.ai.mcp.server.resource-change-notification = true
spring.ai.mcp.server.prompt-change-notification = true
----

When the Spring AI MCP server serves no tools, resources or prompts, for
example with `spring.ai.mcp.server.capabilities.tool=false`, the Camel routes
of that kind are not exposed: the application starts, the routes keep running,
and the starter logs why they are not served. With `MODERN` (see
<<_mcp_protocol_version_2026_07_28>>), such a property only stops Spring AI
from auto-configuring the repository of that kind: a repository the
application defines is still served.

=== Origin validation

Camel's principal-aware HTTP transport is selected only when
`spring.ai.mcp.server.protocol` is `STREAMABLE`, `STATELESS` (see
<<_serving_without_sessions>>) or `MODERN` (see
<<_mcp_protocol_version_2026_07_28>>) and the Camel transport activation
condition is satisfied:

* By default, the Camel provider is selected when `camel.mcp-server.tags` is
  configured and the Spring AI MCP server is of the `SYNC` type (see
  <<_server_type>>). This enables the Origin validator and authenticated
  caller context needed by Camel route capabilities.
* Set `camel.mcp-server.transport-enabled=true` to select the Camel provider
  even when no Camel tags are configured, for example when the application
  exposes only Spring-defined `@McpTool`, `@McpResource`, or `@McpPrompt`
  endpoints but also wants Camel's Origin validation.
* Set `camel.mcp-server.transport-enabled=false` to keep Spring AI's default
  provider even when Camel tags are configured. The Camel bridge remains
  enabled, but the selected provider does not automatically install Camel's
  Origin validator or caller-context extractor.
* When no tags are configured and `transport-enabled` is unset, Spring AI's
  default provider is retained. Applications that expose only Spring-defined
  MCP capabilities therefore do not acquire Camel's loopback-only Origin
  policy as a side effect of adding the starter.

When Camel's provider is selected, it validates the `Origin` header on every
MCP Streamable HTTP request, including `POST`, the SSE `GET`, and `DELETE`:

* A request without an `Origin` header is accepted. Process-based MCP clients
  commonly omit this header.
* A request with an allowed origin is accepted. Any other origin is rejected
  with HTTP 403 before it reaches an MCP operation.
* When `camel.mcp-server.allowed-origins` is not set, only loopback origins
  are allowed: `localhost`, `127.0.0.1`, and `[::1]`, using HTTP or HTTPS and
  any port.
* When configured, the property replaces the loopback defaults. Each entry
  is an exact origin or uses `:*` to match any port.

For example, to allow a remote browser client and local development tools:

[source,properties]
----
camel.mcp-server.allowed-origins = https://app.example.com, http://localhost:*
----

Add the loopback origins explicitly to the list when you still need local
browser-based clients. Scheme and host matching is case-insensitive, and
default HTTP and HTTPS ports are normalized.

If Camel tags or Origin settings are configured while the Spring AI protocol
is unset or uses SSE, the Camel HTTP transport is not installed.
The starter logs a warning because Origin validation and caller-context
extraction are not active in that configuration. Select
`spring.ai.mcp.server.protocol=STREAMABLE` (or `STATELESS` or `MODERN`) when
those protections are required.

With the Spring AI 2.1 WebMVC transports (`STREAMABLE`, `STATELESS` and
`MODERN`), an Origin rejection returns HTTP 403 with a plain-text
`Invalid Origin header` response body.
The rejection occurs before MCP request dispatch, but this response body is
not the JSON-RPC error envelope returned by the Camel Main HTTP engine.
Treat the HTTP status and pre-dispatch rejection as the enforced transport
security boundary; the response-envelope difference remains a runtime parity
limitation of the Spring AI WebMVC transports.

Origin validation is independent of CORS. Configure CORS separately when a
browser client needs cross-origin response access; CORS response headers do
not replace the server-side Origin check.

If the MCP server should only be reachable from the local machine, also bind
the Spring Boot HTTP server to the loopback interface:

[source,properties]
----
server.address = 127.0.0.1
----

An application-provided `WebMvcStreamableServerTransportProvider` takes
precedence over Camel's auto-configured transport. It does not automatically
inherit Camel's Origin validator or authenticated-caller context extractor.
Both helpers are public so a custom provider can reuse Camel's exact origin
normalization, loopback defaults, and caller-context representation.

For example:

[source,java]
----
.securityValidator(CamelMcpServerTransportAutoConfiguration.createOriginValidator(
        "https://app.example.com,http://localhost:*"))
.contextExtractor(request -> SpringAiMcpTransportContext.extract(
        request, Map.of("application", "my-app")))
----

Pass `null` to `createOriginValidator` to use
`CamelMcpServerTransportAutoConfiguration.DEFAULT_ALLOWED_ORIGINS`.
The context-extractor overload composes application-owned entries with
Camel's authenticated caller entry; the reserved Camel context key cannot
be overwritten. The extractor does not authenticate the request. The custom
provider must still be configured with an authentication mechanism and the
appropriate authorization policy. The `camel.mcp-server.allowed-origins`
property is applied only to Camel's auto-configured provider.

To change a few settings of the transport rather than replace it, define
`McpServerCustomizer` beans for its builder, as with Spring AI's own
transports: `McpServerCustomizer<WebMvcStreamableServerTransportProvider.Builder>`
for `STREAMABLE`, `McpServerCustomizer<WebMvcStatelessServerTransport.Builder>`
for `STATELESS` and `McpServerCustomizer<WebMvcModernServerTransport.Builder>`
for `MODERN`. When Camel's transport is selected, they are applied too, in
their order and after Camel's settings, so a customizer takes precedence over
Camel:

* a customizer that sets other options, such as the maximum number of
  sessions or the session idle timeout, keeps Camel's Origin validation and
  authenticated caller context;
* a customizer that sets its own security validator (`securityValidator`, or
  `httpHeaderValidator` for `MODERN`) replaces Camel's Origin validation, and
  `camel.mcp-server.allowed-origins` no longer applies;
* a customizer that sets its own context extractor (`contextExtractor`)
  replaces Camel's authenticated caller context, unless it builds the
  context with `SpringAiMcpTransportContext.extract(request, entries)` as
  shown above.

[source,java]
----
@Bean
McpServerCustomizer<WebMvcStreamableServerTransportProvider.Builder> mcpTransportCustomizer() {
    return builder -> builder
            .maxSessions(1000)
            .sessionIdleTimeout(Duration.ofMinutes(30));
}
----

The streamable HTTP transport has to be selected explicitly with
`spring.ai.mcp.server.protocol=STREAMABLE`; when the property is not set,
Spring AI serves the deprecated SSE transport instead and there is no
endpoint at `/mcp`.

Serving concerns are configured on the Spring AI MCP server — see the
https://docs.spring.io/spring-ai/reference/api/mcp/mcp-streamable-http-server-boot-starter-docs.html[Spring AI MCP server documentation]
for the full list of `spring.ai.mcp.server.*` options. For example:

[source,properties]
----
spring.ai.mcp.server.protocol = STREAMABLE
spring.ai.mcp.server.name = my-integration-app
spring.ai.mcp.server.version = 1.0.0
spring.ai.mcp.server.streamable-http.mcp-endpoint = /mcp
----

=== Server type

Whatever the protocol, the starter serves the Camel routes only on a Spring AI
MCP server of the `SYNC` type: `spring.ai.mcp.server.type=SYNC`, the default.
With `spring.ai.mcp.server.type=ASYNC`:

* the Camel routes are not served, and the starter logs a warning when
  `camel.mcp-server.tags` is configured;
* Spring AI's transport is kept, without Camel's Origin validation and
  authenticated caller context, unless
  `camel.mcp-server.transport-enabled=true` is set with
  `spring.ai.mcp.server.protocol` `STREAMABLE`, `STATELESS` or `MODERN` and
  the stdio transport disabled.

=== Serving without sessions

With `spring.ai.mcp.server.protocol=STREAMABLE`, the Spring AI MCP server keeps
a session for each client in memory: the session ends when the application
restarts, and a request that reaches another instance finds no session, so
several instances need session affinity in front of them.

With `spring.ai.mcp.server.protocol=STATELESS`, Spring AI serves each request on
its own, and the starter registers the Camel routes on that stateless server.
No `Mcp-Session-Id` is returned, so a restart or another instance is invisible
to the client. Camel's Origin validation and caller-context extraction apply as
with `STREAMABLE`, through `WebMvcStatelessServerTransport`; an
application-provided `WebMvcStatelessServerTransport` takes precedence.

[source,properties]
----
spring.ai.mcp.server.protocol = STATELESS
camel.mcp-server.tags = crm
----

Without a session, the server cannot send anything outside the answer to a
request:

* clients are not notified when Camel routes add or remove tools, resources or
  prompts; they see the change at their next list request,
* a `GET` on the endpoint (the stream for server-initiated messages) is answered
  with HTTP 405,
* features that need a server-initiated request, such as sampling or
  elicitation, are not available.

The stateless mode serves the MCP protocol versions that open with an
`initialize` handshake (2025-11-25 and earlier). Protocol version 2026-07-28,
which has no session by design, is served with `MODERN`.

=== MCP protocol version 2026-07-28

With `spring.ai.mcp.server.protocol=MODERN`, Spring AI serves MCP protocol
version 2026-07-28, and the starter adds the Camel routes to that server. A
client of 2026-07-28 has no handshake and no session: every request carries its
protocol version and is served on its own, so a restart or another instance is
invisible to the client. Unlike with `STATELESS`, the client is still told about
changes: when a Camel route adds or removes a tool, resource or prompt, a client
listening with a `subscriptions/listen` request receives the list change.

[source,properties]
----
spring.ai.mcp.server.protocol = MODERN
camel.mcp-server.tags = crm
----

The Camel routes are added to the tool, resource and prompt repositories that
Spring AI auto-configures, next to the application's own tools, resources and
prompts. A Camel route with the name or URI of one of them is refused, as with
the other protocols. A resource with the URI of a resource template, or a
template with the URI of a resource, is refused too, because the Spring AI
resource repository removes both together: when the application registers such
an entry at runtime, after the Camel route, stopping the route removes it as
well, and the starter logs a warning. Camel's Origin validation and
caller-context extraction apply to every request: the starter provides them to
Spring AI's `WebMvcModernServerTransport` as `ServerHttpHeaderValidator` and
`McpTransportContextExtractor` beans, and beans of those types defined by the
application take precedence.

Be aware that:

* Spring AI serves one protocol per application: with `MODERN`, a client that
  opens with an `initialize` handshake (protocol version 2025-11-25 and
  earlier) is answered with HTTP 400 and cannot connect. Clients that try
  2026-07-28 first and fall back to `initialize` connect with 2026-07-28. Camel
  Main and Camel JBang serve both kinds of client on the same endpoint (see
  xref:components:others:mcp-server.adoc[MCP Server]);
* as with the other protocols, only `spring.ai.mcp.server.type=SYNC`, the
  default, is supported (see <<_server_type>>);
* if the application defines its own tool, resource or prompt repository, the
  Camel routes of that kind are not served, and the starter logs a warning;
* protocol version 2026-07-28 is built on the `io.modelcontextprotocol.modern`
  API of the MCP Java SDK, which may still change in minor releases.

=== Connecting MCP clients

Any MCP client can connect over streamable HTTP. Another Camel integration
can consume the tools with the camel-openai MCP client and automatic tool
execution:

[source,java]
----
from("direct:agent")
    .to("openai:chat-completion"
        + "?model={{llm.model}}"
        + "&autoToolExecution=true"
        + "&mcpServer.myCamelTools.transportType=streamableHttp"
        + "&mcpServer.myCamelTools.url=http://localhost:8080/mcp");
----

A coding agent or IDE is configured with the same URL, e.g. in an
`mcp.json`-style client configuration:

[source,json]
----
{
  "mcpServers": {
    "my-integration-app": {
      "type": "http",
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

=== Serving over stdio

Out of the box the tools are served over streamable HTTP: the starter brings
in `spring-ai-starter-mcp-server-webmvc`. MCP clients that launch the server
as a subprocess speak over stdin/stdout instead, which Spring AI serves with
the plain `spring-ai-starter-mcp-server`. Swap the transport starter:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel.springboot</groupId>
    <artifactId>camel-mcp-server-starter</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-mcp-server</artifactId>
    <!-- the Spring AI version of camel-mcp-server-starter -->
    <version>2.1.0</version>
</dependency>
----

The version of `spring-ai-starter-mcp-server` must be the Spring AI version
the starter is built with: the version of `spring-ai-starter-mcp-server-webmvc`
in the POM of `camel-mcp-server-starter`, 2.1.0 in this release. Another
version, including one that the dependency management of the application
imposes, for example with an older Spring AI BOM, can lack MCP Java SDK types
the starter uses, and the application then fails at startup.

Then enable the stdio transport:

[source,properties]
----
spring.ai.mcp.server.stdio = true
spring.main.web-application-type = none
spring.main.banner-mode = off

# stdout carries the MCP protocol, so nothing else may be written to it
logging.threshold.console = OFF
logging.file.name = my-integration-app.log
----

Because stdout carries the MCP protocol, the application must not run as a
web application, the banner has to be switched off and console logging has
to be turned off — writing the log to a file instead. Leaving console
logging on corrupts the protocol stream, as the Spring Boot startup log is
then interleaved with the JSON-RPC messages.

A stdio server is launched by the client instead of being connected to over
a URL:

[source,json]
----
{
  "mcpServers": {
    "my-integration-app": {
      "command": "java",
      "args": ["-jar", "/path/to/my-integration-app-1.0.0.jar"]
    }
  }
}
----

See the
https://docs.spring.io/spring-ai/reference/api/mcp/mcp-server-boot-starter-docs.html[Spring AI MCP Server Boot Starter documentation]
for the transport options and the full list of `spring.ai.mcp.server.*`
properties. On Quarkus the equivalent setup is described in the
https://docs.quarkiverse.io/quarkus-mcp-server/dev/getting-started-stdio.html[quarkus-mcp-server stdio guide].

=== Mixing with Spring-defined tools

Camel tools coexist with tools defined natively in Spring AI — both are
served by the same MCP server and appear in the same `tools/list`. For
example, a `@McpTool`-annotated bean:

[source,java]
----
@Component
public class CalculatorTools {

    @McpTool(name = "add_numbers", description = "Add two numbers")
    public String add(
            @McpToolParam(description = "First addend", required = true) int a,
            @McpToolParam(description = "Second addend", required = true) int b) {
        return String.valueOf(a + b);
    }
}
----

is exposed alongside the `ai-tool` routes. Spring-defined tools are
registered when the server is created; Camel tools are added and removed
dynamically with the route lifecycle. Choose distinct tool names — MCP has a
flat tool namespace.

=== Dynamic tools

The exposed tool list follows the route lifecycle: stopping or suspending an
`ai-tool` route removes its tool, starting or resuming it publishes the tool
again, and connected clients are notified via
`notifications/tools/list_changed`:

[source,java]
----
camelContext.getRouteController().stopRoute("query-db-route");   // tool disappears
camelContext.getRouteController().startRoute("query-db-route");  // tool is back
----

=== Error handling

Results returned to MCP clients are sanitized by the bridge: a route
exception produces an `isError` result with the generic message
`Tool execution failed` (the cause is logged server-side and never sent to
the client), a missing or invalid argument returns the validation message,
and a call exceeding `camel.mcp-server.tool-timeout` returns
`Tool execution timed out` while the route keeps running until it completes
on its own. Resource reads and prompt requests use the corresponding
`camel.mcp-server.resource-timeout` and `camel.mcp-server.prompt-timeout`
settings, each with a default of 20000 milliseconds.

On Camel Main and Camel JBang the equivalent setup is the `camel-mcp-server`
module with the `camel.server.mcp-*` options; on Quarkus it is the
`camel-quarkus-mcp-server` extension.

Define tools as regular `ai-tool` routes and give them tags:

[source,java]
----
from("ai-tool:query_db?tags=crm&description=Query customer database"
     + "&parameter.customerId=string&parameter.customerId.required=true")
    .to("jdbc:dataSource");
----

or in YAML DSL:

[source,yaml]
----
- route:
    from:
      uri: "ai-tool:send_email"
      parameters:
        description: "Send email notification"
        tags: "notify"
        parameter.to: string
        parameter.to.description: "Recipient address"
        parameter.to.required: "true"
        parameter.subject: string
        parameter.priority: string
        parameter.priority.enum: "low,normal,high"
      steps:
        - to: "smtp://mail.example.com"
----

Tool parameters are declared with the `parameter.NAME` options: the value is
the JSON type (`string`, `integer`, `number`, `boolean`), and the
`parameter.NAME.description`, `parameter.NAME.required` and
`parameter.NAME.enum` options refine the generated JSON Schema. Arguments
arrive as message headers in the route (`${header.customerId}`).

Select the tags to expose in `application.properties`:

[source,properties]
----
camel.mcp-server.tags = crm,notify

# per-call execution timeout (milliseconds, default 20000)
camel.mcp-server.tool-timeout = 10000
----

=== Resources and resource templates

Expose a fixed resource with an `ai-resource` route. The route body supplies
the resource content and the component metadata supplies its URI and MIME type:

[source,java]
----
from("ai-resource:app_config?resourceUri=camel:///config/app.json"
     + "&tags=crm&description=Application configuration&mimeType=application/json")
    .setBody(constant("{\\"env\\":\\"production\\"}"));
----

A resource template can expose resources selected by URI path variables:

[source,java]
----
from("ai-resource:customer_template?uriTemplate=camel:///customers/{customerId}"
     + "&tags=crm&description=Customer selected by id&mimeType=application/json")
    .process(exchange -> {
        String customerId = exchange.getMessage().getHeader(
                "CamelAiResourceTemplateVariable.customerId", String.class);

        // Validate the identifier against application policy before using it.
        if (customerId == null || !customerId.matches("[A-Za-z0-9-]{1,64}")) {
            throw new IllegalArgumentException("Invalid customer identifier");
        }

        exchange.getMessage().setBody("{\\"customerId\\":\\"" + customerId + "\\"}");
    });
----

A route declares either `resourceUri` for a fixed resource or `uriTemplate`
for a resource template. Template variables are client input: validate them
before using them in filesystem paths, database queries, authorization
decisions, or downstream requests. Do not treat a syntactically valid URI
variable as proof that the caller may access the referenced data.

Resources and resource templates are selected using the same
`camel.mcp-server.tags` setting as tools. Their registration follows the
Camel route lifecycle.

=== Prompts

Expose a prompt with an `ai-prompt` route. Prompt arguments are strings and
arrive as message headers:

[source,java]
----
from("ai-prompt:greeting?tags=crm&description=Say hello&title=Greeting"
     + "&argument.name.description=Who to greet&argument.name.required=true")
    .setBody(simple("Hello ${header.name}"));
----

A string route result becomes one user message. For a multi-message result,
return a list containing strings and/or maps with `role` and `content` fields.
The supported roles are `user` and `assistant`. Content may be plain text or
an MCP content block:

[source,java]
----
from("ai-prompt:multi_turn?tags=crm&description=Return a user and assistant message")
    .setBody(constant(List.of(
        "Plain user message",
        Map.of("role", "assistant", "content", "Assistant reply"))));
----

Prompt routes follow the same tag selection and route lifecycle rules.
Content assembled from external systems, including resource content and
prompt messages, must be treated as untrusted data. It may contain prompt
injection instructions; do not grant such content authority over system
instructions, tool permissions, or application security policy.

To advertise resource and prompt capabilities and their list-change
notifications, configure the corresponding Spring AI server properties:

[source,properties]
----
spring.ai.mcp.server.capabilities.resource = true
spring.ai.mcp.server.capabilities.prompt = true
spring.ai.mcp.server.resource-change-notification = true
spring.ai.mcp.server.prompt-change-notification = true
----

=== Origin validation

The Streamable HTTP transport validates the `Origin` header on every request
to the MCP endpoint, including `POST`, the SSE `GET`, and `DELETE`:

* A request without an `Origin` header is accepted. Process-based MCP clients
  commonly omit this header.
* A request with an allowed origin is accepted. Any other origin is rejected
  with HTTP 403 before it reaches an MCP operation.
* When `camel.mcp-server.allowed-origins` is not set, only loopback origins
  are allowed: `localhost`, `127.0.0.1`, and `[::1]`, using HTTP or HTTPS and
  any port.
* When configured, the property replaces the loopback defaults. Each entry
  is an exact origin or uses `:*` to match any port.

For example, to allow a remote browser client and local development tools:

[source,properties]
----
camel.mcp-server.allowed-origins = https://app.example.com, http://localhost:*
----

Add the loopback origins explicitly to the list when you still need local
browser-based clients. Scheme and host matching is case-insensitive, and
default HTTP and HTTPS ports are normalized.

With the Spring AI 2.0.2 WebMVC transport, an Origin rejection currently
returns HTTP 403 with a plain-text `Invalid Origin header` response body.
The rejection occurs before MCP request dispatch, but this response body is
not the JSON-RPC error envelope returned by the Camel Main HTTP engine.
Treat the HTTP status and pre-dispatch rejection as the enforced transport
security boundary; the response-envelope difference remains a runtime parity
limitation of the current Spring AI WebMVC transport.

Origin validation is independent of CORS. Configure CORS separately when a
browser client needs cross-origin response access; CORS response headers do
not replace the server-side Origin check.

If the MCP server should only be reachable from the local machine, also bind
the Spring Boot HTTP server to the loopback interface:

[source,properties]
----
server.address = 127.0.0.1
----

A custom application-provided `WebMvcStreamableServerTransportProvider`
takes precedence over Camel's auto-configured transport. It does not inherit
Camel's Origin validator or authenticated-caller context extractor. To retain
caller identity in Camel tool routes, install the public Camel extractor on
the provider builder:

[source,java]
----
.contextExtractor(SpringAiMcpTransportContext::extract)
----

Import
`org.apache.camel.springboot.mcp.server.SpringAiMcpTransportContext`
where the provider is configured. The extractor copies the authenticated
Spring MVC request principal and its Spring Security authorities into the
MCP transport context; it does not authenticate the request. The custom
provider must also configure an Origin validator equivalent to, or stricter
than, the policy described above. The `camel.mcp-server.allowed-origins`
property is applied only to Camel's auto-configured provider.

The streamable HTTP transport has to be selected explicitly with
`spring.ai.mcp.server.protocol=STREAMABLE`; when the property is not set,
Spring AI serves the deprecated SSE transport instead and there is no
endpoint at `/mcp`.

Serving concerns are configured on the Spring AI MCP server — see the
https://docs.spring.io/spring-ai/reference/api/mcp/mcp-streamable-http-server-boot-starter-docs.html[Spring AI MCP server documentation]
for the full list of `spring.ai.mcp.server.*` options. For example:

[source,properties]
----
spring.ai.mcp.server.protocol = STREAMABLE
spring.ai.mcp.server.name = my-integration-app
spring.ai.mcp.server.version = 1.0.0
spring.ai.mcp.server.streamable-http.mcp-endpoint = /mcp
----

=== Connecting MCP clients

Any MCP client can connect over streamable HTTP. Another Camel integration
can consume the tools with the camel-openai MCP client and automatic tool
execution:

[source,java]
----
from("direct:agent")
    .to("openai:chat-completion"
        + "?model={{llm.model}}"
        + "&autoToolExecution=true"
        + "&mcpServer.myCamelTools.transportType=streamableHttp"
        + "&mcpServer.myCamelTools.url=http://localhost:8080/mcp");
----

A coding agent or IDE is configured with the same URL, e.g. in an
`mcp.json`-style client configuration:

[source,json]
----
{
  "mcpServers": {
    "my-integration-app": {
      "type": "http",
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

=== Serving over stdio

Out of the box the tools are served over streamable HTTP: the starter brings
in `spring-ai-starter-mcp-server-webmvc`. MCP clients that launch the server
as a subprocess speak over stdin/stdout instead, which Spring AI serves with
the plain `spring-ai-starter-mcp-server`. Swap the transport starter:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel.springboot</groupId>
    <artifactId>camel-mcp-server-starter</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-mcp-server</artifactId>
    <version>2.0.0</version>
</dependency>
----

and enable the stdio transport:

[source,properties]
----
spring.ai.mcp.server.stdio = true
spring.main.web-application-type = none
spring.main.banner-mode = off

# stdout carries the MCP protocol, so nothing else may be written to it
logging.threshold.console = OFF
logging.file.name = my-integration-app.log
----

Because stdout carries the MCP protocol, the application must not run as a
web application, the banner has to be switched off and console logging has
to be turned off — writing the log to a file instead. Leaving console
logging on corrupts the protocol stream, as the Spring Boot startup log is
then interleaved with the JSON-RPC messages.

A stdio server is launched by the client instead of being connected to over
a URL:

[source,json]
----
{
  "mcpServers": {
    "my-integration-app": {
      "command": "java",
      "args": ["-jar", "/path/to/my-integration-app-1.0.0.jar"]
    }
  }
}
----

See the
https://docs.spring.io/spring-ai/reference/api/mcp/mcp-server-boot-starter-docs.html[Spring AI MCP Server Boot Starter documentation]
for the transport options and the full list of `spring.ai.mcp.server.*`
properties. On Quarkus the equivalent setup is described in the
https://docs.quarkiverse.io/quarkus-mcp-server/dev/getting-started-stdio.html[quarkus-mcp-server stdio guide].

=== Mixing with Spring-defined tools

Camel tools coexist with tools defined natively in Spring AI — both are
served by the same MCP server and appear in the same `tools/list`. For
example, a `@McpTool`-annotated bean:

[source,java]
----
@Component
public class CalculatorTools {

    @McpTool(name = "add_numbers", description = "Add two numbers")
    public String add(
            @McpToolParam(description = "First addend", required = true) int a,
            @McpToolParam(description = "Second addend", required = true) int b) {
        return String.valueOf(a + b);
    }
}
----

is exposed alongside the `ai-tool` routes. Spring-defined tools are
registered when the server is created; Camel tools are added and removed
dynamically with the route lifecycle. Choose distinct tool names — MCP has a
flat tool namespace.

=== Dynamic tools

The exposed tool list follows the route lifecycle: stopping or suspending an
`ai-tool` route removes its tool, starting or resuming it publishes the tool
again, and connected clients are notified via
`notifications/tools/list_changed`:

[source,java]
----
camelContext.getRouteController().stopRoute("query-db-route");   // tool disappears
camelContext.getRouteController().startRoute("query-db-route");  // tool is back
----

=== Error handling

Results returned to MCP clients are sanitized by the bridge: a route
exception produces an `isError` result with the generic message
`Tool execution failed` (the cause is logged server-side and never sent to
the client), a missing or invalid argument returns the validation message,
and a call exceeding `camel.mcp-server.tool-timeout` returns
`Tool execution timed out` while the route keeps running until it completes
on its own.

On Camel Main and Camel JBang the equivalent setup is the `camel-mcp-server`
module with the `camel.server.mcp-*` options; on Quarkus it is the
`camel-quarkus-mcp-server` extension.
